### Roster, watchlist, users and auth

**There are two lists of players per user, and the app spent a long time calling them by one name.** The split is now the vocabulary of the whole codebase:

- The **roster** (`players` on the stored item) is the list the Roster and Feed views report on. It is what the reorder screen edits, what the header search adds to, and what a fantasy team stands in for when `rosterSource` says so.
- The **watchlist** (`watchlist`) is a set of `playerKey` strings followed on the **research board**, independent of the roster. A free agent someone is thinking about picking up belongs on it and not on the roster, and before this the app had nowhere to put him but the list every view reports on.

`store.ts`'s exports are named for that split — `getRoster`, `addRosterPlayer`, `removeRosterPlayer`, `reorderRoster`, `getAllRosterPlayers` against `getWatchlist`, `setWatchlisted`. Note **`getWatchlist` changed meaning**: it used to return the roster and now returns the watchlist's keys. That is deliberate rather than careless — it is the right name for the new thing — and it is safe because the return types differ (`WatchPlayer[]` against `string[]`), so every old call site is a compile error rather than a silent change of behaviour. Two names are deliberately *not* touched: the **`WATCHLIST_TABLE`** environment variable, which infra owns and which a rename would cost a stack update, and the **`/api/watchlist` routes**, which every browser tab open at the moment of a deploy is still calling for its roster. The `WatchPlayer` *type* keeps its name too, being what every report, card and season player in both workspaces is built on; a comment on it says which list it belongs to.

The watchlist is stored as **keys, not entries**. Membership is the whole of what the list is, and the board already holds every row it could mark — a saved copy of the name and the Savant spelling would only be a second and staler one of what the leaderboard carries. It is also why the nightly warmer reads `getAllRosterPlayers()` and not the watchlists: what it warms is the per-player season data a *report* needs, and a watchlisted player has no report until somebody rosters him.

Every `store.ts` export takes `userId` first; the list-manipulation logic — especially `reorderRoster`'s per-kind slot splicing — is unchanged. Backed by DynamoDB (one item `{ userId, players, removed, watchlist, prefs, version }`) when `WATCHLIST_TABLE` is set, else `server/data/watchlist.json`. An empty watchlist is the *absence* of the attribute, the same convention `espn` and `removed` follow, so a user who has never starred anyone and one who has cleared the list are the same stored state.

### The roster is a range of rosters

**The Roster and Feed views report on a span of days, and the list of players those days belonged to is not today's list.** They used to be read as though it were: `/api/report` asked `getRoster` for the roster *now* and drew every one of those players across every day of the range. So a man added this morning arrived on "Yesterday" with a full line he had nothing to do with, and a man dropped this morning vanished from a week he was held for six days of — the second of those being the same shape the fantasy `Starters` filter was already found wrong about, one level up (see **ESPN fantasy league**, *A range is a range of lineups*, which is the same sentence about lineups that this is about rosters).

Answering it needs a **history**, and the roster had none: an entry recorded no join date and a removal deleted it outright. Both halves are now stored.

- **`RosterEntry.addedAt`** — the ET baseball day the player went on the roster, `baseballToday()` (the app's one definition of today, which turns at 3am ET), minted inside `addRosterPlayer` rather than by the route so there is one place that decides what today is.
- **`RosterRemoval`** — a **tombstone** on the item's `removed` list, the whole entry plus a `removedAt`, so the days he *was* held can still be reported on.

The two stamps make a **half-open** interval, `[addedAt, removedAt)`: each is the day its own action happened, and a removal takes effect on the day it is made. The asymmetry is doing real work rather than saving a line. It keeps "remove" meaning remove — press ✕ and he is off today's table on the very next read, which is exactly what `removeFromEditor` on the client already assumes when it drops his row before the refetch lands — while yesterday, which you really did hold him for, still has him. A player added and dropped inside one day was held for no days and leaves no tombstone at all.

**The migration is a fallback read, not a script**, the rule `getEspnCreds` follows for the legacy inline ESPN credential and `researchWatchlistOnly` for the renamed preference: an entry with **no `addedAt` has been there forever** and passes every date test, and a record with no `removed` attribute has never dropped anybody. Both fail in the same direction, which is the only safe one — reading an unstamped entry as *added today* would make every existing user's history appear to begin on the day this deployed, a claim the reader has no way to catch, and would empty every past range in the app on the first load after a deploy. A record therefore acquires its history as its owner uses the app. Checked by hand-editing a record: an entry with the stamp stripped is reported on all three days of a three-day range, exactly as it was before any of this.

**Tombstones are pruned on write** (`HISTORY_DAYS`, 70). `/api/report` caps a span at `MAX_RANGE_DAYS` (62), so a player dropped more than that many days before the latest day anybody can be looking at can never appear on a range that reaches him; 70 is that with a week of slack for a range running into the future. It is pruned in `removeRosterPlayer`, which is the only thing that ever grows the list and so the only place that needs to. Pruning too eagerly fails **into the old behaviour and no further** — a player whose tombstone has gone is absent from that range, which is what every dropped player was from every range before this existed — so the horizon is a storage bound rather than a correctness one, and the item cannot grow for the life of the account.

**`getRosterForRange(userId, start, end)`** is what the report reads, and it answers two things rather than one, because the question has two halves and the app used to answer only the first:

- **`players`** — everyone who was on the roster on **any** day of the range. Live entries first, in their saved order (which is the order the reorder screen set and the summary table reads), then the dropped ones, most-recently-dropped first. A player held on none of the days is not in the list at all.
- **`heldDays`** — per player key, which of those days were his. Always fully populated, so no reader has to know what an absent entry would have meant.

**A player dropped and picked back up inside one range is one entry with the union of his intervals**, not two. The app keys everything on `${kind}-${id}`, so two rows for one man would be two React keys, two summary rows and a doubled `Total`; resolving each interval down to the days themselves and unioning the sets makes that fall out rather than needing a rule. Days rather than intervals is affordable precisely because the range is capped at 62 — a `Set` of date strings is both the cheapest and the least ambiguous way to say it.

**The projection is on the server, in `getReport`, and that is the decision worth recording.** The alternative was to ship the whole report and cut it in `App.tsx`, which is exactly what the fantasy `Starters` filter does with `lineups` — but that filter is a *control the reader works*, so the client has to hold the un-narrowed report to answer for it the moment the toggle goes off. This is not a control: a day you did not hold a player is not yours to see under any setting, so shipping it would be a wire full of somebody else's at-bats and a second definition of "held" living in the client beside the first. `getReport` also already narrows each day to the rostered players as it parses (`dayFilterFor`), so it is the one place that walks the range day by day and the projection costs it nothing. It takes an optional `HeldDays` map and gates **both** of its loops on it — the games he played, and the placeholder games his club played without him — reading the day off the enumerated date rather than off `PlayerGame.date`, so the two are gated by exactly the same thing. Nothing downstream had to be told: the summary table's rows, its `Total` and every feed item all sum `report.games`, so cutting the games is the whole of the change. The map is optional because two callers have no history to consult and mean "every day" — `getPlayerDay`, which answers for a man who may be on nobody's roster, and the fantasy path, whose roster is ESPN's rather than ours.

**"Is he on my roster?" is a different question from "was he on it that day", and every control that asks the first is untouched.** `/api/watchlist` still returns the live roster alone, so `rosterKeys` on the client — the research board's `My Roster` button and its accent baseball, and `PlayerDetails`' `On roster` badge and its Remove — all go on meaning *now*, and `PlayerAdder` still dedupes against the same list, which is what makes a dropped player findable and addable again. The one client-side rule that had to move is the **reorder screen**, which read raw `reports` and would therefore have offered to drag and delete a man who is not on the list it edits; it now filters on `rosterKeys` (see **Client**).

**No cache or snapshot version needed anywhere.** The user record is not a `storage.ts` blob — it carries a `version` for the optimistic write and nothing deserializes it by shape — and neither `PlayerReport` nor any type in `server/src/types.ts` gained a field, so `client/src/types.ts` did not have to be mirrored. `addedAt` deliberately lives on a **store-local `RosterEntry`** rather than on `WatchPlayer`: that type is what every report, season player and card in both workspaces is built on, and when a man joined *your* roster is a fact about this one list.

**Verified against the running server and in a browser**, on a real three-batter roster with the file backend: three players added today are all on "Today" and **none** of them on "Yesterday"; back-dating their stamps to 08-01 / 08-12 / 08-13 and asking for 08-11…08-13 gives the three of them 3 / 2 / 1 days of games against the 3 / 3 / 2 the same call returns with all three held throughout, i.e. the projection cuts days rather than rows. Removing one then leaves a tombstone stamped with today, drops him from "Today" outright, and keeps him on 08-11…08-13 with **only** the two days he was held — the summary table drawing all three rows with his line over those two. The four edge cases were driven directly against `store.ts`: a re-add inside a range comes back as one entry holding the union of both spans (08-04…08-06 and 08-11…08-13), an add and a remove inside one day leaves no `removed` attribute at all, a write prunes an 80-day-old tombstone and keeps a 5-day-old one, and removing one kind of a two-way player leaves the other. In the browser at 1200×900 the edit screen lists the two live players and not the dropped one, and the dropped player's own page offers `Add to roster` rather than the `On roster` badge.

**Saved preferences ride on the same item** (`UserPrefs` — the research board's columns, the **player page's Stats tab columns** beside them, the hide-injured toggle, the mute-audio toggle, the **stat-ranks toggle**, the roster source, the board's `researchInclude` / `researchWatchlist`, and the header search's `recentPlayers`). `statRanks` is the one entry two tables share, and deliberately so: the two *column* entries are two because the board and the Stats tab do not offer the same columns, where this is one boolean about how a number is drawn and the two tables are one vocabulary — see **the research board**, where the badge it turns on is set out. The two column entries are deliberately two: the same vocabulary is behind both, but the Stats tab has six fewer columns to offer (`Opp`, `Ros%` and the five trend columns are meaningless over a span of one player's season), so a single entry would mean a write from a player page silently dropping those six from the board's saved set. Both go through one `setColumnPrefs`, so they cannot come to disagree about what `null` — "back to the defaults" — stores. Each is stored only when it differs from the default, so "off" and "back to defaults" are both the *absence* of a key: nothing saved has to be revisited if a default ever changes. `researchInclude` is the one place that convention needed a second thought — `[]` is a **real** state there (the user has turned all three include buttons off) and is stored as an empty array, so absent-means-default and empty-means-empty are genuinely different; note that it is no longer an empty *board* on its own, since the watchlist can now be the whole of one beside it. Same partition key, same version-conditional write, no second table to provision — and a user's saved state is one read on sign-in. DynamoDB needs no schema change for it, being schemaless past the key. The **file backend was a bare array** before prefs existed and is now `{ players, watchlist, prefs }`; `fileLoad` reads every older shape and the next write saves the newer one, so a dev machine's existing list migrates in place rather than being lost.

**`researchWatchlist` was `researchWatchlistOnly` until the board started unioning the watchlist in rather than narrowing to it** (see **Client**), and the rename is handled the way this codebase handles every stored-shape change: the old key is **read on the way in** and never written, so a preference saved before the change still applies, and `setResearchInclude` **deletes it on every write** so no record ends up holding two answers to one question. A record therefore migrates the first time its owner touches the control — the same as-people-use-the-app rule `getEspnCreds` follows for the legacy inline ESPN credential, and for the same reason: a migration script over every user buys nothing that a fallback read doesn't, and can fail halfway. Checked by stubbing the prefs response: a record carrying only the old key brings the board up identically to one carrying only the new.

### The search remembers who you picked

**`UserPrefs.recentPlayers` is the last five players picked out of the header search, most recent first** — what that field offers before a character has been typed (see **Client**, where the menu it draws is set out). It is a *fifth* per-user list beside the roster, the watchlist and the two column sets, and it is deliberately none of them: it says nothing about who is followed or reported on, only about who was looked up.

**Keys, not entries**, which is the rule the watchlist already follows and is stronger here rather than weaker. The client that draws these rows is holding the season roster anyway — `getSeasonPlayers`, the ~1,400-row list the search itself matches against — so a stored name, club and Savant spelling would only be a second and staler copy of what is already in hand; and a player who has left that list is a player the search cannot find by typing either, so a row for him would open on nothing. It is the app's `${kind}-${id}` key, so a two-way player picked as a pitcher is a different entry from the same man picked as a batter, exactly as he is a different roster entry and a different star. Absence means none, the convention every other preference here follows.

**The write is one key rather than a list, and the server owns the arithmetic** (`setRecentPlayer`): push to the front, drop any earlier copy of the same key, cap at `RECENT_PLAYERS` (5). That is what makes it safe to replay against a newer record the way `setWatchlisted` is — "put this key at the front" cannot lose what a concurrent write added, where a whole list posted by a tab that has been open an hour would quietly overwrite it. **No debouncing**, unlike the column preferences: picking a player is one deliberate act with one write behind it, where ticking a group of columns is one intent and a dozen state changes.

**One press of ＋ now writes to this item twice**, which is a shape the app had not had before, and the dev backend cannot survive it on its own: `mutate` re-reads and replays a lost update against a **version-conditional** put on DynamoDB, while `filePersist` has no version to check and the second writer simply overwrites the first. Measured locally before the fix: the added player reached the roster and his own pick vanished from the history on the very machine it was made on. The client serialises the two (`App.tsx::queueUserWrite`, one promise chain), so the ordering is deterministic on both backends rather than correct on one of them; re-measured after, the roster entry and `recentPlayers: ["batter-680757"]` are both in the record.

**Verified against the running server**: seven picks in a row leave exactly five keys, newest first, with the oldest two gone; re-picking the third of them moves it to the front and the list stays five long with no duplicate (`["batter-3","batter-5","pitcher-4","batter-2","pitcher-1"]`); a malformed key is a 400 (`key must be a player key, e.g. 'batter-660271'`) and writes nothing.

`mutate()` is the read/modify/write with the conflict replay, and its `change` returns a **patch** rather than a whole record: the item now carries a roster, a watchlist, the preferences and the ESPN reference, and a caller that has to restate all four is a caller that will one day drop one of them by omission. `update()` is the roster-only wrapper over it, so every list mutation reads as it always did.

There is deliberately **no module-level cache** in `store.ts`: the old one was never invalidated, so a second instance would serve a stale list and its next write would clobber the first wholesale. Writes re-read, apply the change, and do a version-conditional put, replaying once on a lost update — which is exactly the right resolution for `setWatchlisted`, since "make sure this key is (not) in the list" is idempotent and replaying it against the newer record cannot lose anything.

**Sign-in is the app's own, not Cognito's hosted UI.** `client/src/cognito.ts` speaks to the Cognito Identity Provider endpoint directly — sign up, confirm, sign in, resend, forgot, reset and revoke are each one JSON POST needing no request signing for a public app client and, notably, **no dependency**: `oidc-client-ts` and `react-oidc-context` are both gone, and with them 70KB of the bundle. What that bought is the three things the hosted UI cost: a doorway that looks like the app, errors phrased for a person (`friendly()` — Cognito's own wording is kept only for `InvalidPasswordException`/`InvalidParameterException`, which say exactly which rule was broken and so beat anything written here), and a **sign-out that doesn't leave the site**. That last one was a bug: the old code did `removeUser()` then `signoutRedirect()`, which sends OIDC's `post_logout_redirect_uri` — a parameter Cognito's logout endpoint **does not accept**, it wanting `client_id` + `logout_uri` — so signing out landed on a Cognito error page with the session already half torn down. Now it clears local storage, fires a best-effort `RevokeToken` it deliberately doesn't await, and re-renders. **Google still redirects**, because federating means the browser has to visit the provider — `googleSignInUrl` builds the PKCE authorize URL and `exchangeCode` handles the return leg — but it comes back with an ordinary Cognito refresh token, so from that moment there is one code path for everybody, and a federated user is the only one whose sign-out still takes a redirect (to clear the hosted session cookie, without which signing out and back in silently re-auths the same Google account with no chooser). The five screens are **modes of one component** (`AuthScreen`) rather than five components: they share the email being typed, the password, the in-flight flag and the error line, and splitting them would only mean lifting all four back out. A link between them clears the password (`go()`) where the automatic transitions deliberately carry it, which is what lets confirming a sign-up code sign you straight in instead of asking again — and is why walking sign-in → forgot doesn't leave a failed password sitting in a box labelled "New password". Sign-in uses **`USER_PASSWORD_AUTH`**, which posts the password inside the TLS body where SRP would prove knowledge of it without sending it; the hosted UI posted the same password over the same TLS to the same service, so nothing is newly exposed, and `userSrp` stays enabled on the client so the way back needs no infrastructure change.

`Gate` publishes the ID token to `api.ts` (`setAuthToken`/`setReauthHandler`) **during render, not from an effect** — React flushes a child's effects before its parent's, so an effect there let App's first `/api/players`, `/api/watchlist` and `/api/report` go out with no `Authorization` header and 401. For the same reason the splash is only for a boot with **no session at all**: a background renew must not unmount the app. Concurrent 401s share one exchange (`inFlight`) — App fires three requests on mount, and without it an expired token meant three simultaneous refreshes of the same token.

**Staying signed in.** The session — id/access/refresh tokens, their expiry and a `federated` flag — is one JSON blob in **localStorage** under `sicko:session`. It has to be localStorage: `sessionStorage` is per-tab and dies with the tab, so every new tab and every browser restart threw away a valid refresh token, which is what "it makes you reauthenticate too often" was. ID/access tokens last an hour; `refreshTokenValidity` (infra) is the real re-login interval, since Cognito measures it from issuance and a refresh doesn't reset it — 365 days. **A stored session whose ID token has expired is renewed at boot, not treated as signed out**: a saved token is good for an hour where the refresh token beside it is good for a year, so every return after an hour away (a closed laptop, a new tab the next morning) would otherwise hit the sign-in screen. The gate holds the splash through that one exchange and only shows the sign-in card when *it* fails. While the app is open the token is kept ahead of its expiry by **polling the wall clock** every 30s rather than by a timer set to fire at it — a `setTimeout` sleeps through a closed laptop where a poll notices on the next tick. Note iOS Safari caps script-written storage at 7 days without a site visit, so a phone left alone for a week will still ask again.

### The Google round trip fails at Cognito, and the app used to swallow it

**The report.** A brand-new user opens a fantasy invite link, presses Continue with Google, authenticates, and lands on **Cognito's own hosted login page showing an error, offering to sign in with Google again**.

**Reproduced from CloudTrail rather than argued**, the hosted UI logging every leg of the flow under `cognito-idp.amazonaws.com`. On **2026-08-14 19:33 UTC** (an iPhone, Chrome for iOS):

| time | event | result |
| --- | --- | --- |
| 19:33:16 | `OAuth2_Authorize_GET` (`identity_provider=Google`, `code_challenge_method=S256`, `redirect_uri=https://statcastsicko.com/`) | 302 → Google |
| 19:33:22 | `OAuth2Response_GET` (Google returns, `prompt=consent`) | **`Something went wrong. Please try again.`** |
| 19:33:22 | `Login_GET` | **401** — the hosted page the user was left staring at |
| 19:33:30–39 | the same flow retried **from that page** | succeeds; the federated user is created at 19:33:38 |

**It is Cognito's failure and it happens before the browser ever returns to the app**, which is the single most important thing about it: nothing in this repo runs during the failing leg, and no fix in this repo can stop it. Four candidate causes were checked against the live pool and **all four are clean**, so this is not a misconfiguration:

- **Callback URLs.** `CallbackURLs` are `http://localhost:5173/`, the CloudFront origin, and `https://statcastsicko.com/` + `https://www.statcastsicko.com/`; the app sends `${window.location.origin}/`, and the authorize leg 302s to Google, which it could not do on a mismatch.
- **OAuth flows and scopes.** `code`, `openid email profile`, `AllowedOAuthFlowsUserPoolClient` true, `SupportedIdentityProviders` `[COGNITO, Google]`.
- **The identity provider's attribute map.** `email → email` was already mapped, which is the one required attribute on the pool.
- **Our Lambda triggers.** The pool's only trigger is `CustomMessage`, and its **log group does not exist** — it has never been invoked, so no code of ours has ever run in this path.

**What the trace does establish** is the shape of the failure: the request that fails is the *return* leg, the retry with identical parameters succeeds seconds later, and it is the **hosted-UI session** that Cognito cannot find (hence the 401 on the `/login` it bounces to). Across the CloudTrail window it has happened **three times — 2026-08-08, 08-09 and 08-14 — every one of them on an iOS user agent**, and no desktop attempt has ever failed; two of the three were the very first federated sign-in of a brand-new user, which is why the report reads as "new users can't sign in with Google". **The proximate cause is inferred, not proven**: the pattern is what a WebKit third-party/bounce-tracking cookie mitigation produces on an OAuth hop through `*.amazoncognito.com` — a domain the `identity_provider=Google` short-circuit gives the user no interaction with — and every observed recovery is the retry made *from* that domain's own page, which is the interaction. **The remedy for the cause is infrastructure and is not in this change**: putting the hosted UI on a Cognito **custom domain** under `statcastsicko.com` (`auth.statcastsicko.com`) makes the hop same-site. It is not shipped because it cannot be verified from here and because it carries a manual prerequisite that breaks *all* Google sign-in if missed — `https://auth.statcastsicko.com/oauth2/idpresponse` has to be added to the Google OAuth client's authorized redirect URIs **before** the app is pointed at the new domain.

**What is fixed here is everything on this side of the redirect, and each of the four was measured against the built client before and after.** A failed round trip is going to happen; what must not happen is the app compounding it.

- **A redirect that comes back `?error=` was silently swallowed.** `exchangeCode` reads `code` and answers null when there is none, so the gate fell through to "no stored session" and drew the plain sign-in card — no message, and `?error=…&error_description=…` still in the address bar. `cognito.ts::oauthError()` now reads that half of the redirect *before* the exchange and `friendlyOAuth` gives it words (`access_denied` → `Google sign-in was cancelled.`, everything else → `Google sign-in didn't finish. Try it again.`). Measured: **error line `(none)` → `Google sign-in didn't finish. Try it again.`**
- **A `?code=` with no stashed verifier answered null too**, which is "this was not a callback" said of a callback this tab cannot finish — leaving the code in the URL under a card claiming nothing had happened. It throws `SignInInterrupted` now. Measured: **`(none)` → `Sign-in couldn't be completed in this tab. Try signing in again.`**, with the URL cleaned.
- **Both failure paths threw the deep link away.** The catch rewrote the URL to a bare path, so the query the user arrived on — which for this report is the invite — was destroyed by the very failure they were about to retry from. `restoreQuery()` is now called on the error and throw paths as well as on success. Measured: **`?error=server_error&…` → `?league=INV123`**.
- **StrictMode made the exchange impossible in development.** The boot effect runs twice, `exchangeCode` consumes the single-use PKCE verifier on the first pass, and the second found nothing stashed and reported "not a callback" — so Google sign-in could not work at all under `npm run dev` against a real pool. A module-level promise (`exchangeOnce`) makes both passes await one exchange.

**And the invite itself no longer depends on the round trip at all** — see **ESPN fantasy league**, *The invite code is stored, not carried through the redirect*.

**The Google IdP now maps `email_verified`, which is a correctness fix rather than a fix for the above.** All three federated users in the live pool carry `email_verified: false`, because the pool auto-verifies email by sending a code and a federated user is never asked for one — so Google's own verification was being thrown away, and the claim in every federated ID token is false. The mapping also states **`username: sub` explicitly**: Cognito had added that to the provider itself, CloudFormation replaces `AttributeMapping` wholesale, and a template naming two attributes where the provider holds three is an update that could drop the third — the one that decides a federated user's username, so dropping it risks every existing Google account coming back as somebody new. Stating it makes the update a strict superset (synthesised and checked: `email`, `given_name`, `email_verified`, `username`). **This needs a `cdk deploy`; nothing else in the change does.**

**The confirmation email.** Cognito's default is `no-reply@verificationemail.com` saying "Your confirmation code is 123456" — shared sender, aligned with nothing, naming no product. That is close to the definition of what a spam filter is looking for, and it is why sign-up codes were landing in junk. Both halves are fixed, in different places. *Wording*: a pool has **one** verification template used for sign-up **and** password reset, so anything written there has to be vague enough to cover both — `infra/lambda/cognito-message.ts` is a **CustomMessage trigger**, the only place Cognito exposes which of the two it is (`triggerSource`), and writes each properly. A throw there fails the **sign-up**, not just the email, so the whole thing is wrapped and the response is built and assigned **atomically** — a half-written response is one Cognito must reject, where an untouched one just gets the default. The pool's `userVerification` template is kept as exactly that fallback. *Deliverability*: an SES `EmailIdentity` on `statcastsicko.com` with DKIM (three CNAMEs, written by `Identity.publicHostedZone`), a **custom MAIL FROM subdomain** — `mail.statcastsicko.com`, which is what makes SPF *align*, since without one the envelope sender is an `amazonses.com` domain that passes for Amazon and aligns with nobody, and whose MX/SPF records `mailFromDomain` writes itself, so don't add them by hand — and a **DMARC** record at `p=none`, the one nothing writes for us and now a hard requirement for bulk senders at Gmail and Yahoo. **Whether Cognito actually sends through it is a separate flag** (`sesFromEmail` in cdk context) and that split is deliberate: a new SES account is in the **sandbox**, where it may only email verified addresses, so switching the pool over before production access is granted would turn every sign-up into a `CodeDeliveryFailureException`. The identity is created and verified on one deploy; the flag flips sending on a later one.

`auth.ts::requireUser` sets `req.userId`: the verified Cognito `sub` when `USER_POOL_ID` is set, else `DEV_USER_ID ?? 'local'` — which is what keeps `npm run dev` working with no AWS and no login. API Gateway also carries a JWT authorizer, but that's only an edge filter; this middleware is the single place that decides *which* user. `/api/health` and `/api/config` are the only unauthenticated routes.
