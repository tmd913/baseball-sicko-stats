### Roster, watchlist, users and auth

**There are two lists of players per user, and the app spent a long time calling them by one name.** The split is now the vocabulary of the whole codebase:

- The **roster** (`players` on the stored item) is the list the Roster and Feed views report on. It is what the reorder screen edits, what the header search adds to, and what a fantasy team stands in for when `rosterSource` says so.
- The **watchlist** (`watchlist`) is a set of `playerKey` strings followed on the **research board**, independent of the roster. A free agent someone is thinking about picking up belongs on it and not on the roster, and before this the app had nowhere to put him but the list every view reports on.

`store.ts`'s exports are named for that split — `getRoster`, `addRosterPlayer`, `removeRosterPlayer`, `reorderRoster`, `getAllRosterPlayers` against `getWatchlist`, `setWatchlisted`. Note **`getWatchlist` changed meaning**: it used to return the roster and now returns the watchlist's keys. That is deliberate rather than careless — it is the right name for the new thing — and it is safe because the return types differ (`WatchPlayer[]` against `string[]`), so every old call site is a compile error rather than a silent change of behaviour. Two names are deliberately *not* touched: the **`WATCHLIST_TABLE`** environment variable, which infra owns and which a rename would cost a stack update, and the **`/api/watchlist` routes**, which every browser tab open at the moment of a deploy is still calling for its roster. The `WatchPlayer` *type* keeps its name too, being what every report, card and season player in both workspaces is built on; a comment on it says which list it belongs to.

The watchlist is stored as **keys, not entries**. Membership is the whole of what the list is, and the board already holds every row it could mark — a saved copy of the name and the Savant spelling would only be a second and staler one of what the leaderboard carries. It is also why the nightly warmer reads `getAllRosterPlayers()` and not the watchlists: what it warms is the per-player season data a *report* needs, and a watchlisted player has no report until somebody rosters him.

Every `store.ts` export takes `userId` first; the list-manipulation logic — especially `reorderRoster`'s per-kind slot splicing — is unchanged. Backed by DynamoDB (one item `{ userId, players, watchlist, prefs, version }`) when `WATCHLIST_TABLE` is set, else `server/data/watchlist.json`. An empty watchlist is the *absence* of the attribute, the same convention `espn` follows, so a user who has never starred anyone and one who has cleared the list are the same stored state.

**Saved preferences ride on the same item** (`UserPrefs` — the research board's columns, the hide-injured toggle, the mute-audio toggle, the roster source, and the board's `researchInclude` / `researchWatchlist`). Each is stored only when it differs from the default, so "off" and "back to defaults" are both the *absence* of a key: nothing saved has to be revisited if a default ever changes. `researchInclude` is the one place that convention needed a second thought — `[]` is a **real** state there (the user has turned all three include buttons off) and is stored as an empty array, so absent-means-default and empty-means-empty are genuinely different; note that it is no longer an empty *board* on its own, since the watchlist can now be the whole of one beside it. Same partition key, same version-conditional write, no second table to provision — and a user's saved state is one read on sign-in. DynamoDB needs no schema change for it, being schemaless past the key. The **file backend was a bare array** before prefs existed and is now `{ players, watchlist, prefs }`; `fileLoad` reads every older shape and the next write saves the newer one, so a dev machine's existing list migrates in place rather than being lost.

**`researchWatchlist` was `researchWatchlistOnly` until the board started unioning the watchlist in rather than narrowing to it** (see **Client**), and the rename is handled the way this codebase handles every stored-shape change: the old key is **read on the way in** and never written, so a preference saved before the change still applies, and `setResearchInclude` **deletes it on every write** so no record ends up holding two answers to one question. A record therefore migrates the first time its owner touches the control — the same as-people-use-the-app rule `getEspnCreds` follows for the legacy inline ESPN credential, and for the same reason: a migration script over every user buys nothing that a fallback read doesn't, and can fail halfway. Checked by stubbing the prefs response: a record carrying only the old key brings the board up identically to one carrying only the new.

`mutate()` is the read/modify/write with the conflict replay, and its `change` returns a **patch** rather than a whole record: the item now carries a roster, a watchlist, the preferences and the ESPN reference, and a caller that has to restate all four is a caller that will one day drop one of them by omission. `update()` is the roster-only wrapper over it, so every list mutation reads as it always did.

There is deliberately **no module-level cache** in `store.ts`: the old one was never invalidated, so a second instance would serve a stale list and its next write would clobber the first wholesale. Writes re-read, apply the change, and do a version-conditional put, replaying once on a lost update — which is exactly the right resolution for `setWatchlisted`, since "make sure this key is (not) in the list" is idempotent and replaying it against the newer record cannot lose anything.

**Sign-in is the app's own, not Cognito's hosted UI.** `client/src/cognito.ts` speaks to the Cognito Identity Provider endpoint directly — sign up, confirm, sign in, resend, forgot, reset and revoke are each one JSON POST needing no request signing for a public app client and, notably, **no dependency**: `oidc-client-ts` and `react-oidc-context` are both gone, and with them 70KB of the bundle. What that bought is the three things the hosted UI cost: a doorway that looks like the app, errors phrased for a person (`friendly()` — Cognito's own wording is kept only for `InvalidPasswordException`/`InvalidParameterException`, which say exactly which rule was broken and so beat anything written here), and a **sign-out that doesn't leave the site**. That last one was a bug: the old code did `removeUser()` then `signoutRedirect()`, which sends OIDC's `post_logout_redirect_uri` — a parameter Cognito's logout endpoint **does not accept**, it wanting `client_id` + `logout_uri` — so signing out landed on a Cognito error page with the session already half torn down. Now it clears local storage, fires a best-effort `RevokeToken` it deliberately doesn't await, and re-renders. **Google still redirects**, because federating means the browser has to visit the provider — `googleSignInUrl` builds the PKCE authorize URL and `exchangeCode` handles the return leg — but it comes back with an ordinary Cognito refresh token, so from that moment there is one code path for everybody, and a federated user is the only one whose sign-out still takes a redirect (to clear the hosted session cookie, without which signing out and back in silently re-auths the same Google account with no chooser). The five screens are **modes of one component** (`AuthScreen`) rather than five components: they share the email being typed, the password, the in-flight flag and the error line, and splitting them would only mean lifting all four back out. A link between them clears the password (`go()`) where the automatic transitions deliberately carry it, which is what lets confirming a sign-up code sign you straight in instead of asking again — and is why walking sign-in → forgot doesn't leave a failed password sitting in a box labelled "New password". Sign-in uses **`USER_PASSWORD_AUTH`**, which posts the password inside the TLS body where SRP would prove knowledge of it without sending it; the hosted UI posted the same password over the same TLS to the same service, so nothing is newly exposed, and `userSrp` stays enabled on the client so the way back needs no infrastructure change.

`Gate` publishes the ID token to `api.ts` (`setAuthToken`/`setReauthHandler`) **during render, not from an effect** — React flushes a child's effects before its parent's, so an effect there let App's first `/api/players`, `/api/watchlist` and `/api/report` go out with no `Authorization` header and 401. For the same reason the splash is only for a boot with **no session at all**: a background renew must not unmount the app. Concurrent 401s share one exchange (`inFlight`) — App fires three requests on mount, and without it an expired token meant three simultaneous refreshes of the same token.

**Staying signed in.** The session — id/access/refresh tokens, their expiry and a `federated` flag — is one JSON blob in **localStorage** under `sicko:session`. It has to be localStorage: `sessionStorage` is per-tab and dies with the tab, so every new tab and every browser restart threw away a valid refresh token, which is what "it makes you reauthenticate too often" was. ID/access tokens last an hour; `refreshTokenValidity` (infra) is the real re-login interval, since Cognito measures it from issuance and a refresh doesn't reset it — 365 days. **A stored session whose ID token has expired is renewed at boot, not treated as signed out**: a saved token is good for an hour where the refresh token beside it is good for a year, so every return after an hour away (a closed laptop, a new tab the next morning) would otherwise hit the sign-in screen. The gate holds the splash through that one exchange and only shows the sign-in card when *it* fails. While the app is open the token is kept ahead of its expiry by **polling the wall clock** every 30s rather than by a timer set to fire at it — a `setTimeout` sleeps through a closed laptop where a poll notices on the next tick. Note iOS Safari caps script-written storage at 7 days without a site visit, so a phone left alone for a week will still ask again.

**The confirmation email.** Cognito's default is `no-reply@verificationemail.com` saying "Your confirmation code is 123456" — shared sender, aligned with nothing, naming no product. That is close to the definition of what a spam filter is looking for, and it is why sign-up codes were landing in junk. Both halves are fixed, in different places. *Wording*: a pool has **one** verification template used for sign-up **and** password reset, so anything written there has to be vague enough to cover both — `infra/lambda/cognito-message.ts` is a **CustomMessage trigger**, the only place Cognito exposes which of the two it is (`triggerSource`), and writes each properly. A throw there fails the **sign-up**, not just the email, so the whole thing is wrapped and the response is built and assigned **atomically** — a half-written response is one Cognito must reject, where an untouched one just gets the default. The pool's `userVerification` template is kept as exactly that fallback. *Deliverability*: an SES `EmailIdentity` on `statcastsicko.com` with DKIM (three CNAMEs, written by `Identity.publicHostedZone`), a **custom MAIL FROM subdomain** — `mail.statcastsicko.com`, which is what makes SPF *align*, since without one the envelope sender is an `amazonses.com` domain that passes for Amazon and aligns with nobody, and whose MX/SPF records `mailFromDomain` writes itself, so don't add them by hand — and a **DMARC** record at `p=none`, the one nothing writes for us and now a hard requirement for bulk senders at Gmail and Yahoo. **Whether Cognito actually sends through it is a separate flag** (`sesFromEmail` in cdk context) and that split is deliberate: a new SES account is in the **sandbox**, where it may only email verified addresses, so switching the pool over before production access is granted would turn every sign-up into a `CodeDeliveryFailureException`. The identity is created and verified on one deploy; the flag flips sending on a later one.

`auth.ts::requireUser` sets `req.userId`: the verified Cognito `sub` when `USER_POOL_ID` is set, else `DEV_USER_ID ?? 'local'` — which is what keeps `npm run dev` working with no AWS and no login. API Gateway also carries a JWT authorizer, but that's only an edge filter; this middleware is the single place that decides *which* user. `/api/health` and `/api/config` are the only unauthenticated routes.
