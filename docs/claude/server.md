### Date handling

Dates are computed in **America/New_York**, not UTC — and the baseball day **turns at 3am ET, not midnight**: a 10pm ET first pitch out west finishes around 1am, so at 12:30am the day "Today" should mean is still the one whose games are ending, and a calendar rollover would swap the user onto an empty slate mid-game. `server/src/etDate.ts` owns this for the server (`DAY_ROLLOVER_HOUR`, `baseballToday()`, `easternDate()`, `addDays()`, `daysBetween()` — the last of these parsing both ends as **UTC midnight** rather than local, since an ET-local `Date` would put a DST boundary between two dates 23 or 25 hours apart and round the wrong way twice a year) and `index.ts` (the API's default date), `savant.ts` (`isMutable` — on the calendar boundary alone, a 12:30am read called a date whose games were still in progress a frozen past date) and `warmer.ts` all read it. `client/src/App.tsx` mirrors it by hand for its presets, since the workspaces can't share code — the two **must agree**, or a default and a "Yesterday" click land on different dates. `/api/report` accepts `start`/`end` (or legacy `date`), swaps if reversed, and caps the span at `MAX_RANGE_DAYS` (62).

### Server routing notes

- All async routes are wrapped in `asyncRoute()`, which catches and returns `502 { error }`. The client's `api.ts` unwraps that `error` field into thrown `Error`s.
- Endpoints: `/api/players` (season roster), `/api/research` (the league board — see below), `/api/prefs` (GET the user's saved preferences; `PUT /api/prefs/research-columns` takes `{ kind, keys }`, `keys: null` meaning "back to defaults"; `PUT /api/prefs/hide-injured` takes `{ hide }`; `PUT /api/prefs/mute-audio` takes `{ mute }`; `PUT /api/prefs/research-include` takes `{ include, watchlist }`). Deliberately a route per preference rather than one merging `PUT /api/prefs`: their update semantics genuinely differ — a boolean is always set, a column list is per board and needs a null that *clears* — and explicit, tightly-validated routes beat a merge protocol with null-versus-absent rules. The **fourth is the first to carry two fields**, and for a reason the others don't have: the research board's three include buttons and its watchlist filter are one *control set*, read together every time the board decides who is on it and held together by the client whenever either moves, so splitting them would be two writes to one item to express one intent. `include: null` is "back to the default"; `[]` is the real, storable state of someone who has turned all three off. `PUT /api/prefs/roster-source` takes `'saved'` or `'fantasy'`, and accepts the `'watchlist'` an older tab still sends as a synonym for the first., `/api/watchlist` (GET/POST/DELETE `:id?kind=`, plus `PUT /order` for drag-to-reorder — see **Player keys**) — **the user's *roster*, despite the path**: renaming a route breaks every tab open at the moment of a deploy and buys nothing a comment can't say, so the old word survives in the URL and nowhere else, `/api/watch` (GET the **watchlist** as `{ keys }`; `PUT { key, on }` stars or unstars one — player keys, shape-validated against `/^(batter|pitcher)-\d{1,9}$/`, since membership is the whole of what that list is and the board already holds every row it could mark), `/api/espn` (GET status / PUT connect / DELETE disconnect) and `/api/espn/ownership` (see **ESPN fantasy league**), `/api/report`, `/api/percentiles/:playerId`, `/api/players/:playerId/splits`, `/api/players/:playerId/xwoba`, `/api/players/:playerId/arsenal`, `/api/players/:playerId/gamelog`, `/api/statuses`, `/api/video/:playId`. The splits route serves the details view's **Season** tab — the whole-season line plus the vs-L/R splits — and exists for the player who **isn't** on the roster, the report already carrying both for watchlisted players. A pitcher's season line there carries **both ERA-scale estimators**, fetched alongside it rather than after it: xERA off the one league-wide leaderboard, and xFIP via `getSeasonArsenal`'s batted-ball mix — that pitcher's own season CSV, but the same blob the Arsenal tab opens on and already warm for a watched pitcher. `withEstimators` (exported from `savant.ts`) does the filling, and the CSV's throw is **caught here**: a failed estimator must cost one number, not the whole tab. The arsenal route serves a pitcher's **season** arsenal (`getSeasonArsenal` + the league table) as `{ pitches, vsRight, vsLeft }` — each a `SeasonArsenalPitch[]` sorted by usage, with the splits null when he's faced nobody of that hand — for the details view's Arsenal tab. `getSeasonArsenal` runs the same `aggregate()` three times over the CSV, filtering on `stand` (the **batter's** side); usage `share` is relative to the selected view, so a split's shares still add to 100% — the per-game equivalent already rides along on the report as `PitchMix`. The gamelog route (`gameLog.ts`, `?type=pitcher` for the pitching half) serves the details view's **Game Log** tab: one row per game of the season from `stats(type=[gameLog])`, **newest first** — the reverse of the API's order, and the order a game log is read in. It filters to `gameType === 'R'`, since a spring or exhibition line otherwise lands mid-log with stats nobody means to read, and carries the batter's HBP/SF/total bases (never shown as columns) so the client's season row can recompute OBP/SLG from the totals rather than averaging 150 per-game rates. **The rate fields in a game log are season-to-date through that game, not the game's own** — a 1-for-4 night reads `.248` — so they're named `seasonAvg`/`seasonObp`/`seasonSlg`/`seasonOps`/`seasonEra` and the table labels those columns **Szn**. A pitcher's `decision` is derived from the log's `wins`/`losses`/`saves`/`holds` tallies in scorebook order rather than named, and a team-abbreviation map (24h) turns the split's `opponent.id` into "MIL" — a full team name is three times the width of the column. **The score and the batting order come from the season's schedule, not the log** — a gameLog split carries the opponent and `isWin` but no score at all, so `getSchedule(season)` pulls the whole regular season in one `schedule?season=…&hydrate=lineups` call (fields cut to the two scores and the lineup ids, ~650KB, cached 30 min like the log and shared across players). `toEntry` turns the score around to his side as `teamScore`/`opponentScore`, which is what lets the row read "W 5-3" without saying who was home; the batter's `lineupSpot` is his index in his side's posted order. **Every *completed* game in that response carries both lineups** — only scheduled and postponed ones don't, and those have no log rows — but a player who came off the bench is in neither, so an unlisted batter gets no spot rather than a guess. A failed fetch costs the rows their score and spot, not the log. A pitcher's **`firstInning`/`lastInning`/`entryMargin`** (the Inn and Ent columns — which innings he was in for, and his team's margin at his first pitch) are in the game log even less: they come off `getSeasonArsenal`'s pitch-level CSV, whose rows stamp every pitch with its inning and the score *before* it (`fld_score` is the fielding side, i.e. his), reduced to one `Appearance` per `game_pk` by `appearanceMap`. The entry row is the lowest `at_bat_number`/`pitch_number` of the game, not the first row seen — the CSV's order isn't guaranteed. That's the same blob the Arsenal tab opens on, and its rejection is caught here: a failed CSV costs two columns, not the tab. Savant lags the feed by a day, so the newest game usually has neither yet. Cached in-memory 30 min, matching the season lines. The xwoba route (`xwoba.ts`) fetches a batter's full-season Savant statcast-search CSV (`batters_lookup[]`) and returns the per-PA xwOBA sequence for the details view's rolling-xwOBA chart; the client computes the rolling averages. Cached in-memory 6h.
- **`/api/statuses`** is `getReport`'s handful of *today* facts for the whole league at once: each player's roster status, and where his club's game has him (`lineupStatus`/`lineupSpot`, `pitchingRole`/`entryInning`, and the game's `gameState`). It exists because the two views that draw a player's status on his headshot — the **research board** and the **details view** — open on players who are not on the roster and so have no `PlayerReport` to read it off, and neither is going to pull a report per row to learn that a man is batting third or on the 10-day IL. `getPlayerStatuses` (in `savant.ts`, beside `getReport` because it reuses that file's `lineupStatusFor`/`pitchingRoleFor` and the same `rosterGame` probable-pitcher test) costs nothing either view wasn't already paying: it is `getDay(baseballToday())` — the same parse the watchlist reads, cached ten minutes and fifteen seconds while a game is live — joined to `getAllRosterStatuses()`, which is the same 30 team 40-man rosters `getRosterInfo` fetches *whole* to answer for one player on them, on the same 30-minute per-team cache. A failed roster read is caught and costs the IL badges while leaving the lineup pips, which is the right direction to fail in: the day is the half that changes by the minute. **Three passes, in order**: the day's boxscore rosters and announced probables give each player his side of a game; the day's own parsed reports then override per kind (a reliever's entry inning exists nowhere but in the game he pitched, and merging per kind keeps a two-way player's bat from overwriting his arm); and finally everyone with *no* game today but an off-active status, who is precisely the player this is most worth saying something about. **Only players something is true of are shipped** — `saysSomething` drops the plainly-active man with no lineup posted, who is otherwise 26 a side of pure payload, and `gameState` is in that test only because a postponement is itself a fact about his day. ~600 entries on an unposted morning, ~1,100 once a day's lineups and bullpens are in; ~100KB of JSON, which `compression()` takes to a tenth of that.
- `store.ts::reorderRoster` deliberately keeps any roster players missing from the submitted `keys`, so a stale client can't drop or bury players.
- Express 5 (path-to-regexp v8) rejects a bare `'*'` route — the SPA fallback is path-less middleware that serves `client/dist/index.html` for non-`/api` GETs.
- **Video** (`/api/video/:playId`) is resolved lazily, from **two sources with opposite failure modes**, only when a clip is opened. MLB's own `game/{gamePk}/content` highlights are tried first — joined on `guid`, which is the same Statcast playId threaded through the rest of the app — and Savant's `sporty-videos` page is scraped for a `sporty-clips.mlb.com/*.mp4` second. The order is the important part: MLB's cuts land **during** the game but are curated (15 of 82 plate appearances on a checked game), while **Savant covers essentially every play but is a day behind** — its page 200s with an identical 88KB JS shell, no `<video>` in it, for a playId it hasn't ingested yet. So the current day is the highlights or nothing. Two caching rules follow from that, and getting either wrong empties the day's video: **the highlight reel is persisted only once the game is final** (`content-{gamePk}-v2.json`, gated on a 98-byte status probe — the reel *grows as the game is played*, and the old code wrote whatever existed the first time anyone opened a clip and kept it forever, which for three of five games checked on 2026-08-09 was **no clips at all**, and for the rest 2–3 where the finished game has 15–18), and an empty reel isn't persisted even then, since cuts can land minutes after the last out. **A resolved URL is cached permanently and a miss for ten minutes** — today's miss is tomorrow's clip, so a null kept forever is unrecoverable inside a warm Lambda. The `-v2` on the key is what invalidates every blob written under the old rule. **A reel item that shares its video with another is dropped, both of them** — MLB's own join is occasionally wrong: on 2026-08-10 the "Soderstrom swipes home" item carried the *RBI double's* asset (same `mediaPlaybackId`, same caption file), so the feed's steal played a hit from four batters earlier. The guid and the join were both right; the reel was wrong. Nothing in the payload says which of the two owns the asset — each item's slug correctly names its own play — so neither keeps it and both fall through to Savant, which has them the next day. Showing nothing is an absence the UI already handles; showing the other play's clip is a lie about what happened. It costs next to nothing: zero collisions across 113 clips on eight finished games. The clip streams directly to the browser `<video>` (hotlink-protected by User-Agent, which a real browser satisfies) — the server never byte-proxies it. Every clip in the app plays through **`ClipVideo.tsx`**, which manages the native controls on touch devices: iOS keeps its control bar up for seconds after playback starts and a clip only runs six to twelve, so the bar covers the bottom of the frame — the plate — for much of it, with no way to shorten the timeout and no hover to summon it back. Under `(hover: none)` it therefore drops `controls` on play, restores them on pause/end, and pauses on a tap; that tap is armed on **`pointerdown`**, not judged when the click arrives. The native controls are shadow DOM, so a tap on the play button reaches this element too, and by the time its `click` is dispatched the `play` event has already flipped the state and re-rendered — so a handler bound on "am I playing *now*?" (which is what this used to do) is bound in time to catch the very tap that started playback, and every clip stopped dead the instant it began. Down-then-up is one gesture: if the finger went down while the controls were up, the tap belongs to them, whatever the state is when it lifts. Anything with a pointer keeps the browser's own controls. The **highlight reel** (`GameReel.tsx`, the "Highlights" button on a final game's block) is purely client-side: it resolves each of the player's at-bats' last-play clips via the same `/api/video` route (sequentially, so the first call warms the per-game highlight cache) and plays them back to back in one `<video>`. There is no server-side concatenation.
